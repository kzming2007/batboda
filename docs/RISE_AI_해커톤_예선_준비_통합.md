### 07-22 특강에서 제시된 조언

다음은 강연자의 해커톤 경험에 기반한 조언이며 공식 평가 기준이나 확정 규칙이 아니다. 상세 분석은 `docs/20260722_좋은_서비스_구현을_위한_특강_인사이트.md`에서 관리한다.

- 기능을 늘리기보다 핵심 문제의 해결 방법론을 깊게 만들고, 그 방법을 심사위원이 한 번에 이해하게 전달한다.
- 지정 문제는 낯설어도 탐색 범위가 제한되어 핵심 로직에 집중할 수 있다. 자유 문제는 문제의 실재성과 중요성부터 팀이 입증해야 하므로 탐색 부담이 더 클 수 있다.
- 도메인 검증에는 책·논문·공식 지침 같은 기준 자료가 필요하며, AI가 만든 수치나 가중치 자체를 근거로 삼지 않는다.
- AI 반복 탐색은 고정된 근거·입력·평가 함수·중단 조건·사람 승인을 갖춘 경우에만 적용한다.
- 차별화는 부가기능보다 정확도, 효율, 예외 처리, 설명 가능성에서 만든다.
- 소개서는 하나의 핵심 메시지, 예상 UI, 기술 구조가 기억에 남도록 구성한다.
- 1분 영상은 기능 목록보다 실제 사용 맥락과 핵심 입력→분석→결과 흐름을 보여준다.
- 로그인·관리자 화면 등 핵심 문제와 무관한 기능은 초기 MVP에서 제외한다.

### 팀이 확인한 현재 결정

- 2인으로 참가한다.
- 팀원은 남궁도현, 김택명이며 모두 인공지능학과다. 매몰을 막기 위해 개인 강점은 현재 역할 근거로 기록하지 않는다.
- 주말에는 두 팀원 모두 정오부터 작업할 수 있다. 평일별 가용시간은 아직 확정하지 않았다.
- 문제정의서 1 `기업 문제`로 참가한다.
- 예선 MVP의 구체적 사용자는 `특정 지역 또는 후보 농지를 정하고 첫 작물을 준비하거나 재배를 막 시작했지만, 표준 지식과 실제 토양·최근 기상·예보의 차이를 해석하기 어려운 예비·초기 귀농인`으로 정의한다. 농지 계약 전 사용자만으로 한정하지 않는다.
- 1분 영상은 `문제→위치·작물·기간 입력→공공데이터 분석→재배 판단 단계·선택 기간 위험→예방 행동→한 문장 결론` 구성으로 제작한다.
- 단기 결과 명칭은 사용자가 고른 기간을 반영하는 **`선택 기간 재배 위험도`**로 사용한다. 지원할 기간 범위와 입력 UX는 실제 예보 API 범위를 확인한 뒤 확정한다.
- 재배 희망 농지 입력은 현재 위치와 지도 선택을 함께 검토하되, 현재 위치와 실제 농지가 다를 수 있으므로 `농장 위치 확인`을 반드시 거치도록 설계한다. 세부 UX는 아직 확정하지 않았다.
- 대표 시연 농지·작물은 에이전트가 근거와 구현 부담을 비교해 후보를 제안하되, 사용자가 검토한 뒤 확정한다.
- Antigravity Mock은 요구사항·지도 상호작용·실패 사례의 참고 원본으로 보존하고 실제 제출 프로토타입의 구현 기반으로 사용하지 않는다.
- 실제 제출용 프로토타입은 `prototype/codex-mvp`에 Next.js·TypeScript 기반으로 새로 구축한다. 공공데이터 키는 서버에서만 사용하고, 규칙 기반 분석과 화면을 분리한다.
- 기존 UI의 작은 폰트와 낮은 정보 위계·배치 가독성은 개선 대상으로 확인했고, API 데이터 계약·필지 정합·실패 처리 고정 후 2026-07-23 1차 구조 개편을 반영했다. 제출 화면으로 동결하기 전 실제 사용 흐름, 숫자 지수의 시각적 비중, 모바일·녹화 화면 가독성을 다시 검토한다.
- **미확정 UI 아이디어:** PASS·금융 앱의 인증 시작 화면처럼 간결한 첫 화면에서 분석에 필요한 기본정보를 순서대로 입력하게 한다. 실제 회원가입·로그인·본인인증 기능은 추가하지 않고, 위치·작물·기간 등 분석 시작 정보를 받는 온보딩 표현만 참고한다. 대시보드 바로 진입 방식과 비교해 이해 속도가 빨라지는지, 1분 시연에서 불필요한 단계가 되지 않는지 확인하기 전에는 구현하지 않는다.
- 2026-07-24 팀은 결과를 `적합 / 조건부 적합 / 현장 확인 필요`의 단계 판정 중심으로 전달하기로 확정했다. 숫자 지수는 성공 확률이나 예측값처럼 강조하지 않고, 단계 판정이 나온 계산 근거를 확인하는 보조 정보로 둔다.
- 다음 UI 정리에는 문구 감사를 포함한다. `AI가 분석했습니다`처럼 주체와 근거가 모호한 표현, 영어 장식어, 내부 개발 용어, 과장된 확신 문구를 줄이고 `확인된 자료`, `최근 날씨 기록`, `재배 전 확인할 점`처럼 초보 귀농인이 바로 이해할 표현을 우선한다. 공식 API·토양 코드처럼 정확성이 필요한 용어는 쉬운 설명과 함께 병기한다.
- Figma Education 인증은 사용자 확인 기준으로 완료됐다. 실제 UI 개선 단계에서 계정 화면의 사용 가능 기능·할당량, Codex 연동 범위, 산출물 이관 부담을 확인한 뒤 사용한다. 현재는 Figma 플러그인을 설치하거나 디자인 산출물을 만들지 않는다.
- 2026-07-23 현재 Codex MVP의 지도 선택→작물·1/3일 기간 선택→팜맵·토양·단기예보 조회→규칙 기반 판단선→예방 행동 흐름을 구현했다. MVP 위치 입력은 지도 핀과 대표 시연지 단축 선택으로 구현했으며, 현재 위치 기능은 후속 검토 항목으로 남긴다.
- 평창 대관령 시연 좌표에서 팜맵 후보 30개, 토양 PNU·경계·pH·유기물·검정시점·시료 유형, 기상청 단기예보의 실응답을 확인했다. 팜맵 첫 후보와 토양 PNU가 달랐으므로 첫 항목 자동 선택을 폐기하고 토양 PNU·팜맵 ID와 일치한 후보만 확정한다.

## 6. 서비스 소개서와 1분 영상

### 서비스 소개서

공식 안내와 OT 설명을 합치면 다음 내용이 필요하다.

1. 지역 산업 문제와 AI 역할이 드러나는 서비스 제목
2. 문제, 사용자, AI 역할, 결과물을 포함한 5~7문장 요약
3. 문제를 발견하거나 주제로 선정한 이유
4. 좁고 구체적인 타깃 사용자
5. 활용 데이터와 서비스 내부 사용 방법
6. AI가 담당하는 기능과 판단 과정
7. 시행착오와 개선 시도
8. 사용한 공공데이터·도구와 서비스 아키텍처
9. 입력값과 출력값, 핵심 기능, 시연 화면

공식 Google Slides 양식은 팀 Drive에 사본을 만든 뒤 가이드 문구를 지우고 작성한다. 제출 전 `링크가 있는 모든 사용자–뷰어` 권한과 비로그인 접근을 확인한다.

특강 조언을 적용해 소개서 전체를 관통하는 한 문장을 먼저 정하고, 예상 제품 UI와 `입력→공공데이터→규칙 기반 계산→설명→화면`의 책임 분리를 시각적으로 보여준다. 이는 공식 양식의 필수 항목을 대체하는 것이 아니라 이해 속도를 높이기 위한 구성 원칙이다.

### 1분 시연영상

- 실제 입력→데이터 조회·처리→결과 흐름을 보여준다.
- 서비스 소개서에서 주장한 핵심 기능이 화면에 나타나야 한다.
- 완제품 수준의 정교함보다 핵심 워크플로우가 작동하는지가 중요하다.
- 시연용 샘플·캐시를 사용하면 실시간 데이터처럼 오해되지 않게 표시한다.
- Google Drive 또는 공식 안내가 허용하는 영상 URL을 제출하고, 비로그인 상태에서 재생되는지 확인한다.
- 실제 프로토타입 화면을 중심으로 사용자·사용 시점·판단 결과를 보여준다. 생성형 영상이나 합성 화면을 쓰면 실제 구현과 구분한다.

팀은 다음 60초 구성을 사용하기로 합의했다. 구간별 초수는 편집 과정에서 소폭 조정할 수 있지만 서사 순서는 유지한다.

| 구간 | 내용 |
|---|---|
| 0~7초 | 초보 귀농인의 지역·작물 판단 문제 |
| 7~17초 | 농지 위치와 작물 입력 |
| 17~35초 | 공공데이터 조회와 규칙 기반 분석 |
| 35~50초 | 적합도, 위험 요인, 근거, 신뢰도 |
| 50~57초 | 예방 행동 또는 대안 |
| 57~60초 | 서비스의 한 문장 결론 |

## 7. 문제 트랙 대조

### 문제정의서 1 — 기업 문제

초보 귀농인이 지역과 작물을 입력하면 토양·기상 공공데이터를 이용해 환경 적합성을 분석하고 위험 요소와 예방 가이드를 받는 서비스다.

- 대상 작물: 사과, 배, 오이, 감자, 상추
- 데이터 후보: 기상청, 흙토람 등 공식 농업·기상 데이터
- OT에서 강조한 핵심:
  - 정답 산식이 미리 주어진 문제가 아니다.
  - 공식 자료·논문 등을 조사해 팀이 설명 가능한 계산식을 구성해야 한다.
  - 변수별 가중치, 예외 처리, 작물별 특이사항, 결측·이상치 처리가 중요하다.
  - 계산 결과를 챗봇이나 리포트로 설명하고 실제 사용 가능한 UI/UX로 보여준다.

### 문제정의서 2 — 지역 문제

학교 밖 청소년이 경험·관심·학력 등을 입력하면 공공데이터와 NCS·복지·훈련 정보를 바탕으로 자립 로드맵을 받는 서비스다.

- 대상 연령 안내: 약 19~25세
- 진로 범위를 몇 개 분야로 좁혀 설계
- 핵심 부담: 텍스트 구조화, 역량 매핑 신뢰성, 실제 지원정보 연결, 따뜻하지만 부정확하지 않은 안내

### 문제정의서 3 — 자유 문제

실제 사람들이 반복적으로 겪는 지역·기업 문제를 직접 정의하고, 공공데이터를 이용해 AI 서비스 프로토타입으로 해결한다.

- 문제의 실재성과 규모를 팀이 직접 입증해야 한다.
- 준비된 기업·지역 문제는 문제 영향력이 이미 제시되어 있지만, 자유 문제는 영향력부터 설득해야 한다.
- 자유 문제에 공식적인 감점이 있다고 단정하지 않는다.

## 8. 기업 문제 구현 검증 게이트

기업 문제 선택은 확정했다. 다만 위치 입력 방식, 데이터 조합, 산식, 프로토타입 범위는 다음 사실을 검증한 뒤 확정한다.

1. 지역 입력을 기상·토양 조회 단위 또는 좌표로 변환할 수 있는가
2. 기상청·흙토람 계열 API 중 현재 실제 호출 가능한 항목은 무엇인가
3. 다섯 작물의 생육 기준을 어떤 공식 자료·논문에서 확보할 것인가
4. 적합도 가중치와 점수 산식을 한 장에서 설명할 수 있는가
5. 결측·이상치·API 장애에서 어떤 결과를 보여줄 것인가
6. LLM 설명이 계산 결과를 왜곡하지 않도록 어떻게 제한할 것인가

실호출 검증 결과 기본 운영은 **실시간 우선 + 소스별 명시적 대체**로 정한다. 개발 중 대체값은 Mock으로 명시하고, 제출 영상 안정성을 위한 검증 캐시는 출처·수집시각·재현 절차를 갖출 수 있을 때만 추가한다.

| 전략 | 구성 | 구현 부담 | 심사 위험 |
|---|---|---:|---:|
| 완전 실시간 | 토양·기상 API를 모두 실시간 호출 | 매우 높음 | 요구 충족 시 낮음 |
| 실시간+검증된 캐시 | 실시간 호출을 우선하고 실패 시 출처가 있는 캐시 사용 | 높음 | 캐시 표기가 명확하면 중간 |
| 정적 시연 | 준비된 데이터로 화면과 흐름을 시연 | 낮음 | 공공데이터 연동·운영 가능성에서 높음 |

실응답 필드와 수정 파이프라인은 `docs/20260723_공공데이터_실응답_파이프라인_감사.md`를 따른다.

Codex/GPT-5.6 Sol 우선은 모델 간 절대 성능을 확정한 결론이 아니라 현재 운영 조건에 따른 기본값이다. 모든 프로젝트 자료가 이 작업공간에 있고, 조사→파일 수정→코드 실행→테스트→검토를 한 흐름으로 관리할 수 있기 때문이다. OpenAI 공식 가이드도 GPT-5.6 Sol을 복잡하고 개방적인 고가치 작업, 복잡한 코드, 깊은 조사, 완성도 높은 문서의 우선 선택지로 안내한다.

Claude Team은 중복 작업용이 아니라 독립 검토용으로 사용한다. 다음 상황에서는 Claude를 먼저 또는 함께 사용한다.

- VOD에서 소개한 Cowork 기능을 그대로 재현해야 할 때
- Codex 초안과 다른 관점의 서비스 설명·사용자 흐름이 필요할 때
- 소개서나 1분 영상 대본을 제출 전에 반대 관점으로 검토할 때
- Claude Team 계정의 실제 기능·제약을 확인하는 작은 실험을 할 때

### 개발 환경과 서비스 런타임 구분

- Codex/GPT-5.6 Sol과 Claude Team은 현재 **개발·조사 작업 환경**이다.
- 배포된 프로토타입에서 GPT 또는 Claude를 호출하려면 별도의 API Key, 권한, 크레딧, 이용약관 확인이 필요하다.
- 어느 웹 계정을 받았다는 사실만으로 해당 모델 API를 서비스에 연결할 수 있다고 가정하지 않는다.
- API가 확보되지 않으면 규칙 기반 계산과 검증된 정적 설명으로 시연하고, LLM 연동은 확장 항목으로 명시한다.
- LLM 제공자·모델·비용·키는 교체 가능한 런타임 변수로 남긴다. 규칙 엔진이 만든 근거 묶음을 구조화 입력으로 전달하고, 출력 형식·금지 표현을 검증한 뒤 실패하면 같은 근거의 규칙 기반 문장으로 대체하는 계약을 먼저 구현한다. LLM이 적합도 수치나 판정을 새로 계산하지 않는다.

### 우선순위 재평가

절대적인 모델 우열을 가정하지 않는다. 필요하면 동일한 입력과 평가표로 다음 두 작업을 Codex와 Claude에 각각 수행해 비교한다.

1. 기업 문제 공식 자료에서 요구사항·미확인 사항·출처를 추출하는 작업
2. 같은 근거로 서비스 요약 5~7문장과 1분 시연 구성을 만드는 작업

비교 기준은 사실 오류, 출처 누락, 수정 횟수, 산출물 사용 가능성, 소요시간이다. 유의미한 차이가 확인될 때만 기본 우선순위를 조정한다.

### 공통 안전 원칙

- VOD 쿠폰, 계정 정보, API Key, password, token을 외부 문서나 저장소에 기록하지 않는다.
- AI가 만든 숫자·출처·농업 조언은 원문과 대조한다.
