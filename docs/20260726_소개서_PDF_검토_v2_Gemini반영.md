## 1. 8장은 코드와 일치한다

`contract.ts`의 `validateReport()`가 확인하는 항목은 다음 다섯이다.

```
판정 단계 인용 / 금지 표현 / 근거 묶음 밖 숫자 / 필수 구성 / 길이
```

소개서 8장의 서술(`판정을 그대로 인용했는지 / 쓰면 안 되는 표현이 없는지 / 근거에 없는 숫자를 새로 만들지 않았는지 / 세 부분 구성을 지켰는지 / 길이가 적절한지`)과 **정확히 맞다.** 과장이나 없는 기능을 적은 부분이 없다.

금지 표현 목록도 실재한다 — `성공 확률`, `발병 확률`, `보장`, `처방`, `진단`, `AI가 판단`, `추천 품종` 등 13개.

## 2. 핵심 발견 — 7장 문장이 다섯 항목을 통과하면서 세 가지를 틀렸다

7장에 실린 Gemini 출력이다.

> 토양 pH는 6.9로 상추 재배 기준인 6.5–7.0 안에 들지만, **밭 적성등급이 2급지이고 배수 조건이 '약간 양호'하여 저습하거나 물 고임이 생길 수 있습니다.** … 위험 등급은 '주의'입니다. … 대관령면 85-61번지 밭은 …

### 왜 통과했는가 (코드 기준 추적)

| 검사 | 결과 | 이유 |
|---|---|---|
| 판정 단계 인용 | 통과 | `조건부 적합`이 한 줄 결론에 있다 |
| 금지 표현 | 통과 | 목록에 `수확량은`이 있는데 문장은 `수확량을`이다. 한 글자 차이로 비켜갔다 |
| 근거 묶음 밖 숫자 | 통과 | 6.9·6.5·7.0·2·3·22.8·15·20 모두 근거 묶음에 있다 |
| 필수 구성 | 통과 | 세 부분 모두 있다 |
| 길이 | 통과 | 범위 안 |

### 무엇이 틀렸는가

**(1) 데이터 값을 추론 결과로 바꿨다**

`저습`은 토양특성 V3의 **저해요인 필드에 적힌 값**이다. 이미 확정된 사실이다. Gemini는 이걸 `배수 약간 양호 → 저습이 생길 수 있다`는 **예측**으로 뒤집었다. 있는 값을 없는 인과로 만들었다.

**(2) 좋은 값을 부정 근거로 썼다**

`2급지`는 밭 적성등급에서 **두 번째로 좋은 등급**이다. 화면에서도 `밭으로 쓰기에 조건이 좋은 땅`으로 설명한다. 그런데 문장은 `2급지이고 … 하여 물 고임이 생길 수 있습니다`로 이어 붙여 감점 근거처럼 만들었다.

`배수 약간 양호`도 6단계 중 상위권인데 `하여 저습`으로 연결됐다.

**(3) 확정한 용어를 다르게 썼다**

| 확정 용어 | Gemini가 쓴 말 |
|---|---|
| 선택 기간 재배 위험도 / 가까운 3일 위험 | **위험 등급** |
| 대관령면 85-61전 | **85-61번지 밭** |

기준 문서는 단기 위험 결과를 `선택 기간 재배 위험도`로 표현하기로 정했다. 지번도 공식 표기는 `85-61전`이다.

### 이것이 뜻하는 것

다섯 항목은 **숫자와 라벨의 존재 여부**를 본다. **값들 사이의 관계**는 보지 않는다. 그래서 다음이 통과한다.

- 근거에 있는 값들만 써서 **틀린 인과를 만드는 문장**
- 판정 라벨은 인용하면서 **위험 라벨은 마음대로 바꾸는 문장**

**심사에서 나올 질문**: "AI가 근거를 왜곡하면 어떻게 걸러냅니까?" 지금은 답이 없다.

## 3. 권고 — 저비용으로 막을 수 있다

세 가지를 더하면 위 세 문제 중 둘을 바로 막고, 하나는 크게 줄인다. 모두 `lib/report/contract.ts` 안에서 끝나므로 **제공자 코드와 무관하게 병합된다.**

### 3-1. 위험 라벨도 인용 검사에 넣는다 (즉시)

지금은 판정 단계(`조건부 적합`)만 검사한다. 위험 라벨(`주의`)을 같은 방식으로 추가한다. **(3)의 절반이 막힌다.**

### 3-2. 프롬프트에 인과 금지 규칙을 넣는다 (즉시)

검증기로 인과를 판정하는 것은 어렵다. 대신 생성 단계에서 막는다.

> 근거 묶음의 값을 서로 원인과 결과로 연결하지 않는다. 각 값은 적힌 그대로 서술한다.
> 저해요인·배수·등급은 이미 확정된 값이므로 `~하여 ~가 생길 수 있다`처럼 예측으로 바꾸지 않는다.
> 등급과 배수는 좋고 나쁨을 임의로 판단하지 않고, 근거 묶음에 적힌 해석 문구를 쓴다.

**(1)과 (2)를 크게 줄인다.**

### 3-3. 금지 표현 목록의 구멍을 메운다 (즉시)

`수확량은`만 있어서 `수확량을`·`수확량이`가 통과한다. `성공 가능성`도 목록에 없다. 어미 변화에 걸리지 않게 **어간 단위로 바꾼다** (`수확량`, `성공 가능`).

### 3-4. 소개서에 이 한계를 적는다

10장에서 삭제할 `AI 미연결` 행 자리에 넣는다.

> **AI 문장 검사가 값의 관계까지 보지는 않는다** / 판정 인용·금지 표현·새 숫자·구성·길이 다섯 항목을 검사하고, 통과하지 못하면 규칙 문장으로 되돌린다 / 프롬프트에서 인과 연결을 금지하고, 위험 라벨 인용 검사를 추가

**한계를 먼저 말하고 대응을 붙이면 강점으로 읽힌다.** 8장이 이미 그 구조다.

## 4. Gemini 연결로 새로 생긴 소개서 보완점

### 4-1. 모델 버전을 밝힌다

4장은 `Google Gemini API`, 8장은 `Gemini`로만 적혀 있다. **`Gemini 2.5 Flash`로 명시할 것을 권한다.** 모델을 고른 이유(빠른 응답, 낮은 비용)가 함께 읽히면 판단이 있었던 것으로 보인다. 지금은 그냥 갖다 쓴 것처럼 읽힌다.

### 4-2. 비용·지연·실패 처리를 한 줄 넣는다 ★ 운영 가능성 25점

유료 외부 API가 **실행 경로 안에** 들어왔다. 심사가 물을 것이 늘었다.

- 호출 비용은 어떻게 감당하는가
- 응답이 늦으면 사용자는 얼마나 기다리는가
- 키는 어떻게 관리하는가
- 실패하면 화면이 비는가

**네 번째는 이미 답이 있다**(규칙 문장으로 되돌림, 8장). 앞의 셋을 한 줄로 추가하면 배점 항목을 직접 겨냥한다.

> 설명 문장만 생성하므로 호출당 토큰이 작고, 빠른 모델(Gemini 2.5 Flash)을 골랐습니다. 응답이 실패하거나 검사에 걸리면 기다리지 않고 규칙 문장으로 되돌립니다. 인증키는 서버 환경변수로만 사용합니다.

`인증키는 서버 환경변수로만 사용합니다`는 양식 5장이 요구한 민감정보 조건에도 맞는 서술이다.

### 4-3. 같은 입력에 문장이 달라지는 문제를 선점한다

LLM은 호출마다 표현이 달라진다. 심사가 `매번 다른 말이 나오면 신뢰할 수 있나`를 물을 수 있다.

답은 이미 설계에 있다. **판정과 수치는 규칙이 고정하므로 결론은 바뀌지 않고 표현만 바뀐다.** 8장 마무리에 한 줄로 넣으면 질문을 미리 막는다.

### 4-4. 4장 API 표에서 Gemini를 분리한다

공공데이터 6개와 `Google Gemini API`가 한 표에 섞여 있다. 성격이 다르고, v1에서 지적한 **`네 갈래` vs `6개` 혼선**을 키운다.

> **공공데이터 (6)** — 팜맵 · 토양특성 V3 · 토양검정 V2 · 단기예보 · 농업기상 기본 · 농업기상 관측지점
> **생성 AI (1)** — Gemini 2.5 Flash · 판정 결과를 초보자의 말로 옮기는 설명 문장

이렇게 나누면 3장의 `자료 네 갈래`와도 충돌하지 않는다.

### 4-5. 화면 탭 이름과 소개서가 어긋날 수 있다

김택명 PC에서 04 페이지 탭 이름을 `LLM 기반 리포트` → **`쉬운 말 리포트`**로 바꾸고 `예시 문안` 배지를 삭제했다. **당시 LLM이 연결되지 않았기 때문에 화면이 사실과 다른 주장을 하지 않게 한 조치였다.**

이제 Gemini가 연결됐으므로 그 전제가 사라졌다. 병합된 코드에 이 이름이 남아 있으면, 소개서는 `AI가 쓴 설명`이라 하고 화면은 AI를 언급하지 않는 상태가 된다. **시연 화면·영상과 소개서가 어긋난다.**

두 가지 중 하나로 정한다.

- 탭 이름을 `LLM 기반 리포트`로 되돌린다. 이제는 사실이다
- 또는 `쉬운 말 리포트`를 유지하고 화면에 `Gemini 2.5 Flash 생성 · 검사 통과` 같은 작은 표시를 붙인다

**두 번째를 권한다.** 이름은 사용자 말로 두고, 출처는 표시로 밝히는 편이 이 서비스의 원칙(자료 출처를 항상 표시한다)과 일관된다.
